# cfn-workbench: design handoff

A reporting surface for the design team. This document describes **what the page is, what it must communicate, and the engineering constraints any design must respect.** It deliberately does not prescribe color, typography, layout, density, or component styling. Those are yours to propose.

---

## 1. What this is

`cfn-workbench` renders a single HTML progress page for one run of a CFN Loop (a long, multi-agent software task). A "run" can take many iterations; each iteration produces tests, screenshots, review manifests, and a pass/fail verdict.

**Readers:** the engineer who launched the run, and anyone reviewing it afterward. They want fast answers to:
- Is it passing right now?
- What changed in the latest iteration?
- What is blocked or unresolved?
- What is the overall verdict?

**Lifecycle of the page:** generated fresh at any checkpoint (idempotent: same inputs produce the same output). It is opened from `file://`, attached to a run folder, or dropped into a chat. It is rarely "browsed" like a website; it is scanned under time pressure during a run, then read more carefully post-mortem.

A functional first draft already exists (renderer source: `.claude/skills/cfn-workbench/`). Treat it as a **data-shape reference**, not a visual brief. You may run it to see real data; do not treat its current appearance as a constraint or a starting aesthetic.

---

## 2. Hard engineering contract (non-negotiable)

Any design must operate within these. They are not aesthetic preferences; they are how the artifact ships.

- **One self-contained HTML file.** No external requests of any kind: no stylesheets, no web fonts, no scripts, no remote images. The file must render correctly from `file://` with no network.
- **No JavaScript.** All interactivity must be native HTML (e.g. `<details>`). No frameworks.
- **Images are inlined** as `data:` URIs (base64). There can be many screenshots per iteration; a cap limits how many embed.
- **All interpolated content is HTML-escaped.** The page renders untrusted strings (test output, review findings, evidence text). Design must never assume "clean" text.
- **Generated by bash + jq**, not a web stack. Anything requiring a build step, a component tree, or runtime templating is out of scope. The design is expressed as static HTML + inline CSS.
- **Idempotent render.** The page is regenerated frequently. Nothing may rely on client-side state or "first visit" behavior.
- **Variable width.** Read on a desktop monitor, a laptop, a tablet, and occasionally a phone. Long runs produce long pages.
- **No em dashes** anywhere in rendered copy (project rule). Use periods, commas, colons, or parentheses.

---

## 3. Information inventory (the 8 sections)

Each section maps to a data source. Some are dense; some are frequently empty. The full list, with what each communicates:

1. **Header** (always present) — run slug, branch, iteration count, overall verdict, generation timestamp.
2. **Iteration timeline** — one cell per iteration: pass rate, gate verdict, commit count. Runs range from 1 iteration to 15+.
3. **Per-iteration detail** — the deepest section. Per iteration: lane results (which parallel work-stream passed/failed), test summary line, gate events (which review skills ran and their verdicts), and a screenshot grid. At 15 iterations this is the bulk of the page.
4. **Acceptance criteria (AC) table** — the definition of done, one row per criterion. Column count **varies** between sources: some tables have 3 columns, some 5, some 8, some 9 (an optional "reference" column). The table must tolerate all of these. Each row carries a status (pass/fail/...) and free-text evidence.
5. **Vote ledger** — every suggestion raised by review skills, with its category, impact/effort, and disposition (accepted/rejected/open).
6. **Tech-debt ledger** — a filtered view of suggestions tagged as tech debt.
7. **Bless ledger** — structural changes made vs. the approved plan (what was supposed to change, what predicates were touched). Has its own verdict.
8. **Footer** — the command that generated the page, input count, HTML size, and a **data-gaps** list (which expected sources were missing).

### Status vocabulary (recurring across sections)
States that appear as labels throughout: `pass`, `fail`, `in-progress`, `pending`, `completed`, `accepted`, `rejected`, `open`, `blocked`, `aborted`, `unknown`, `blessed`. A single design treatment should cover all of them consistently. Some are positive, some negative, some neutral/informational, some signal failure of the run itself.

### Empty states are common
Real runs frequently have: no screenshots, no bless ledger, no test output yet, missing acceptance-criteria results, no lane reports. "No data yet" is a normal state during a run, not an error. The page records every missing source as a data gap (footer). How absence vs. error vs. "still running" should read is an open question.

---

## 4. Data sources (what the design can assume exists)

- Review manifests (JSON): gate events, suggestions, verdicts.
- `VERIFY_<slug>.md`: the acceptance-criteria table + embedded manifest.
- `VERIFY_RESULTS_<slug>.json`: per-criterion status and evidence.
- Bless ledger JSON: structure/predicate changes + verdict.
- Lane reports: per-work-stream pass rates.
- Test output text: the runner's summary line(s).
- Screenshots (PNG): per iteration, can be numerous.
- Git log: branch, commit count.

Every source except manifests is **optional**. Missing sources become data gaps. The design must gracefully handle any subset being absent.

---

## 5. Open questions for the design team

These are problems to solve, not directions. We have no preferred answers.

- **Scanability under time pressure.** During a live run the reader wants the verdict and the latest iteration's status in seconds. How should the most important signals surface, given 8 sections of very different density?
- **Scaling across iteration count.** One iteration vs. fifteen change the page dramatically. How should the per-iteration detail scale so a long run stays navigable?
- **Hierarchy across heterogeneous sections.** A 9-column AC table, a screenshot grid, a one-line test summary, and a gap list all share the page. What is the right information hierarchy?
- **Communicating state.** A dozen status values recur. Some are pass/fail, some are lifecycle (pending/completed), some flag run-level failure (aborted/blocked). How should the reader tell apart "fine", "waiting", and "broken" at a glance, consistently across every section?
- **Absence vs. error.** Missing data is normal mid-run but can also indicate something went wrong. How should the page distinguish "not yet" from "broken"?
- **The data-gaps list.** This is often the most diagnostic part of the page (it tells you what the renderer could not find). It currently lives in the footer. Is that the right home and prominence?
- **Tables on small screens.** The AC table can have up to 9 columns of mixed text and free-form evidence. Mobile is a real (if secondary) reading context.
- **Verdict as the headline.** The single most important value on the page is the overall run verdict. How prominent should it be, and how should it relate to the iteration timeline beneath it?

---

## 6. What we are NOT asking for

- Do not treat the current draft's appearance as a constraint.
- Do not assume a web platform, build tools, or JavaScript. See section 2.
- Do not optimize for first-time novelty over repeated scanning. This page is read many times by the same person during one run.
- No marketing, branding, or "product page" framing. This is an internal engineering instrument.

---

## 7. What success looks like

A reader can, within a few seconds of opening the page, answer: *is the run passing, what is the verdict, and is anything blocked?* On a longer look they can trace what changed in the latest iteration and what evidence supports the current state. This holds across 1 iteration and 15, across desktop and phone, and whether or not most data sources are present.

Everything else (how it looks achieving that) is up to you.

## 8. Transit map contract (shipped)

The map section (`lib/section-map.sh`, `#sec-map`) draws the run as a transit system: one station per lane, grouped into left-to-right wave columns; one vertical trunk per column and one arrowed connector between consecutive waves; a gate junction on the shared connector line; a loop-back edge when the gate failed and a new iteration started; a train per in-flight lane; and a legend naming the status fills. The contract:

- **Inputs are read-only and optional.** The wave layout comes from `planning/<slug>/lanes-<slug>.json` (`waves`: array of lane-id arrays, nested-first via `plan_path`, legacy flat fallback). With no lanes file the section falls back to grouping the run plan's `phases`, then to a single sorted column. Missing run plan and lanes file records a data gap and renders the empty-state card. The section never blocks or fails the render.
- **No new events.** Status is derived entirely from existing data: latest `lane-report-<slug>-*-<lane>.json` with a non-null `blocked_on` makes a station `blocked`; otherwise `landed` / `in-flight` / `pending` exactly as the Roster derives them. The gate junction state comes from the latest `gate_verdict` event (`pass` / `fail` / `unknown` when absent). Iteration count is the number of `loop_started` events, minimum 1.
- **Static-complete without JS.** Every station, track, gate, loop-back, badge, and train is plain SVG with the train position baked at render time. The single inline script (guarded by `prefers-reduced-motion`) only animates trains between their baked endpoints; with JS off or reduced motion requested, the baked positions are the truth. This is the same degrade-to-static rule as the header staleness pill.
- **Geometry invariants.** All coordinates are computed in one jq pass as integers and clamped; bash interpolates integers only. viewBox is sized to content: width = `min(960, gateX + 70)` (compact plans leave no dead space right of the gate; wide plans clamp at 960), height = `70 + maxRows*rowH + 60`. The layout is trunk-and-connector: exactly ONE horizontal connector per adjacent wave pair (plus one into the gate), all on a shared line at y=42 above the first station row, so connectors can never cross; the gate connector stops 30 units short of the gate ring so the arrowhead kisses it without crowding. Column steps are capped (`min(780/(W-1), 340)`) so few-wave maps center instead of spanning wide. Each multi-station column gets one vertical trunk behind its stations (single-station columns emit no trunk) and a wave-colored header (`wave N`) above it at y=20. Stations sit at `y = 70 + k*rowH` where k is the index WITHIN the wave, and height is sized to the tallest column (the +60 covers the corridor and bottom label zone), with rowH stepping down at 7 and 13 lanes so 15+ lanes stay on one page. Connector arrowheads inherit the connector's stroke color (`fill: context-stroke`); the loop-back keeps its own red-tipped marker and ends below-left of column 1's first station, clear of its label; its depth derives from the tallest column's label bottom (`labelBottom + 26`), so the curve clears every station label by ≥15px in every rowH tier. A `map-legend` row naming the four status fills, the train pill, the iterate loop and the gate is required under the SVG. All interpolated text (lane ids, names, status labels) passes through `html_escape`, including `data-lane` attributes; hostile ids and names render as text, never markup.

## 9. Project dashboard contract (shipped)

`dashboard.sh` + `lib/section-map-all.sh` render every loop run in a project as
its own transit line on one self-contained page (`#sec-dashboard`). Where the
per-run map answers "how is this run going", this answers "what is every
session doing right now" in a single tab.

- **Discovery scoping is the contract.** A run is discovered by its PLAN or its
  ROOT-LOCAL event stream: `planning/*/run-plan-*.json` (per-plan dirs),
  `planning/run-plan-*.json` (legacy flat), and plan-less runs with a
  `<root>/tmp/cfn-events-<slug>.jsonl`. Machine-global `/tmp/cfn-events-*`
  files NEVER discover a run: they carry no project marker, so scanning them
  would paint foreign runs onto this project's page. They still enrich an
  already-discovered run (same merge rule as the roster). Runs sort by last
  activity, newest first.
- **Band geometry.** viewBox height 104 per band, line at y=54, stations at
  `x = 60 + idx*step + wave*36`, step clamped `[34, 74]`, gate ring at
  `lastX + 46`, viewBox width `max(gateX + 60, 960)`. The jq TSV protocol uses
  fixed arities: `hdr w h` (3), `st lane status x y label` (6), `conn x1 x2 y`
  (3), `wtick x label` (2), `train lane x1 y x2 y mx depart` (7), `loop path
  mx my` (4), `gate x y` (3). Bash does no float math; jq floors to integers.
- **Label readability zoning.** Station labels sit ABOVE the line (rel y=-22,
  abs 32); wave-tick labels (`W1`, `W2`, ...) get their own row above them
  (abs y=20, tick line y 44-52); the dashed loop-back curve and `iterate`
  label live BELOW the line (curve 66-92, label y=98). Zones never overlap, so
  no label can collide with the curve, the ticks, or each other. Label width
  scales with station spacing: `maxch = floor((step-8)/6)` clamped `[4, 14]`
  (mono 10px ≈ 6px/char); the full name rides in the station `<title>`. The
  gate ring carries NO text label (the run-header chip and `<title>` carry it).
- **Page rules.** Default cap 12 bands (`--max-lines` overrides; hidden runs
  counted in an overflow note). `--live <secs>` injects a same-page meta
  refresh. Self-containment and escaping guarantees are identical to the
  per-run page; exit 0 on empty state (a dashboard is never a gate), exit 2 on
  usage errors.
