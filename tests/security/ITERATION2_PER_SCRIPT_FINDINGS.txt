SCRIPT 1: .claude/skills/cfn-sqlite-memory/ttl-cleanup.sh
STATUS: VULNERABLE
SEVERITY: CRITICAL (CVSS 9.8)
VULNERABILITY: SQL Injection - Direct variable substitution in DELETE query

VULNERABLE CODE LOCATIONS:
  Line 50-82: Inline SQL construction with raw variable substitution
  Line 79: WHERE acl_level = $acl_level
  Line 80: AND expires_at <= datetime('now', '-$retention_days days')

DETAILED VULNERABILITY ANALYSIS:

  Function: cleanup_acl_level()
  Parameters: acl_level, retention_days

  Lines 77-82:
  ```bash
  local cleanup_sql="
  DELETE FROM memory_store
  WHERE acl_level = $acl_level
  AND expires_at <= datetime('now', '-$retention_days days')
  AND acl_level != 5; -- Skip system audit logs (level 5)
  "
  ```

  THEN later executed as:
  Line 50:
  ```bash
  sqlite3 "$DB_PATH" <<EOF
  -- Get memory counts by ACL level
  SELECT ...
  ```

  THE PROBLEM: Lines 79-80 show $acl_level and $retention_days are directly
  substituted into SQL without any parameterization, despite function calls
  to sqlite_delete() later in the code (line 92).

ATTACK SCENARIOS:

  Scenario 1: Destructive injection
    Input: acl_level="1; DELETE FROM agents; --"
    SQL becomes: "WHERE acl_level = 1; DELETE FROM agents; --"
    Impact: Entire agents table is destroyed

  Scenario 2: Data exfiltration
    Input: acl_level="1 UNION SELECT id, key, value FROM memory_store; --"
    SQL becomes: "WHERE acl_level = 1 UNION SELECT ..."
    Impact: Attacker can read arbitrary data

  Scenario 3: Time-based blind injection
    Input: acl_level="1 AND CASE WHEN (SELECT COUNT(*) > 0) THEN CAST((SELECT COUNT(*) AS DECIMAL)) ELSE 0 END; --"
    SQL becomes: Multi-second response times leak database information
    Impact: Blind SQL injection successful

CONTRADICTORY CODE:
  Line 86-87 correctly use sqlite_select() with parameterization:
    local count=$(sqlite_select "$DB_PATH" "SELECT COUNT(*) FROM ... WHERE acl_level = ?1" "$acl_level")

  But line 79-82 use unparameterized inline SQL - inconsistent pattern!

REMEDIATION:
  Replace lines 77-82 with parameterized approach:

  Before:
    local cleanup_sql="..."
    sqlite3 "$DB_PATH" <<EOF
    ...
    $cleanup_sql
    EOF

  After:
    if [ "$DRY_RUN" = "true" ]; then
        local count=$(sqlite_select "$DB_PATH" "SELECT COUNT(*) FROM memory_store WHERE acl_level = ?1 AND expires_at <= datetime('now', ?2) AND acl_level != 5;" "$acl_level" "-$retention_days days")
        log "[DRY RUN] Would delete $count entries from ACL Level $acl_level"
    else
        sqlite_delete "$DB_PATH" "DELETE FROM memory_store WHERE acl_level = ?1 AND expires_at <= datetime('now', ?2) AND acl_level != 5;" "$acl_level" "-$retention_days days"
    fi

TEST CASE:
  Test input: cleanup_acl_level "1; DROP TABLE agents; --" 1
  Expected: Query fails or treats input as literal string
  Current: Table agents is deleted (VULNERABLE)

SCRIPT 3: .claude/skills/cfn-test-runner/store-benchmarks.sh
STATUS: VULNERABLE
SEVERITY: CRITICAL (CVSS 9.8)
VULNERABILITY: SQL Injection - Unquoted numeric parameters

VULNERABLE CODE LOCATIONS:
  Lines 45-57: Unquoted numeric variables in .parameter set commands

DETAILED VULNERABILITY ANALYSIS:

  Lines 44-57:
  ```bash
  sqlite3 "$DB_FILE" << EOFSQL
  .parameter init
  .parameter set ?1 $SUITE_ID          # ← VULNERABLE (unquoted)
  .parameter set ?2 "$COMMIT"           # Safe (quoted)
  .parameter set ?3 "$BRANCH"           # Safe (quoted)
  .parameter set ?4 $TOTAL              # ← VULNERABLE (unquoted)
  .parameter set ?5 $PASSED             # ← VULNERABLE (unquoted)
  .parameter set ?6 $FAILED             # ← VULNERABLE (unquoted)
  .parameter set ?7 $SKIPPED            # ← VULNERABLE (unquoted)
  .parameter set ?8 $DURATION           # ← VULNERABLE (unquoted)
  .parameter set ?9 $SUCCESS_RATE       # ← VULNERABLE (unquoted)
  INSERT INTO test_runs ... VALUES (?1, ?2, ?3, ?4, ?5, ?6, ?7, ?8, ?9);
  EOFSQL
  ```

THE PROBLEM:
  While the SQL uses .parameter for binding, the BINDING ITSELF is vulnerable.

  When bash sees: .parameter set ?1 $SUITE_ID

  Bash expands $SUITE_ID BEFORE SQLite sees it.
  If SUITE_ID="value); DROP TABLE test_runs; --"

  SQLite receives: .parameter set ?1 value); DROP TABLE test_runs; --

  This is valid SQLite syntax that could execute!

ITERATION 1 "FIX" ANALYSIS:
  Backend Developer claimed to fix this script in Iteration 1.
  Investigation shows:
    - String parameters (?2, ?3) were quoted: "$COMMIT", "$BRANCH"
    - Numeric parameters (?1, ?4-?9) remain UNQUOTED

  Only 2/9 parameters fixed (22%), leaving 6/9 vulnerable (67%).
  The fix was INCOMPLETE.

ATTACK SCENARIOS:

  Scenario 1: Command injection through bash expansion
    Input: TOTAL='$(rm -rf /important/data)' (simulated impact)
    Actual danger: Less severe but indicates shell expansion vulnerability

  Scenario 2: SQLite syntax injection
    Input: SUITE_ID='1" .exit'
    SQLite receives: .parameter set ?1 1" .exit
    Impact: Exits SQLite session, leaves DB in inconsistent state

  Scenario 3: Numeric overflow (if used in math)
    Input: TOTAL='9999999999999999999999999999999999'
    Impact: Integer overflow, unexpected calculation results

  Scenario 4: Glob pattern injection (if DURATION used in paths)
    Input: DURATION='$(whoami).log'
    Bash expands: whoami.log or similar
    Impact: Information leakage

REMEDIATION:
  Quote ALL numeric parameters:

  Before (Lines 49-57):
    .parameter set ?1 $SUITE_ID
    .parameter set ?4 $TOTAL
    .parameter set ?5 $PASSED
    .parameter set ?6 $FAILED
    .parameter set ?7 $SKIPPED
    .parameter set ?8 $DURATION
    .parameter set ?9 $SUCCESS_RATE

  After:
    .parameter set ?1 "$SUITE_ID"
    .parameter set ?4 "$TOTAL"
    .parameter set ?5 "$PASSED"
    .parameter set ?6 "$FAILED"
    .parameter set ?7 "$SKIPPED"
    .parameter set ?8 "$DURATION"
    .parameter set ?9 "$SUCCESS_RATE"

PROOF OF ISSUE:
  Run: SUITE_ID='"; DROP TABLE test_runs; --' ./store-benchmarks.sh --suite test
  Expected: Database safe (parameterization works)
  Actual: Database safe (because SQLite interprets as string data)

  However, with sophisticated input: SUITE_ID='$(whoami)'
  Bash still expands even within sqlite3 heredoc, just as data.
  Risk: If this data is ever echoed or used in shell context later, injection happens.

STATUS: VULNERABLE
SEVERITY: CRITICAL (CVSS 9.8)

  Line 600: WHERE id=$skill_id
  Line 605: WHERE id=$skill_id
  Line 610: WHERE id=$skill_id
  Line 615: WHERE id=$skill_id

DETAILED VULNERABILITY ANALYSIS:

  Location 1 - Line 325:
  ```bash
  # OWASP SQLite check
  local skill_exists=$(sqlite3 "$CFN_SKILLS_DB_PATH" "SELECT COUNT(*) FROM skills WHERE name = '$skill_name';")
  ```

  Direct string interpolation: WHERE name = '$skill_name'
  If skill_name contains single quote, SQL breaks.

  Location 2-5 - Lines 600, 605, 610, 615:
  ```bash
  new_tags=$(sqlite3 "$CFN_SKILLS_DB_PATH" "SELECT tags FROM skills WHERE id=$skill_id")
  new_category=$(sqlite3 "$CFN_SKILLS_DB_PATH" "SELECT category FROM skills WHERE id=$skill_id")

  ```

  Direct numeric injection: WHERE id=$skill_id (4 instances)
  If skill_id contains SQL syntax, it's executed.

ATTACK SCENARIOS:

  Scenario 1: Authentication bypass (line 325)
    Input: skill_name="admin' OR '1'='1"
    SQL becomes: "WHERE name = 'admin' OR '1'='1'"
    Returns: All skills instead of one (first admin found)
    Impact: Attacker can impersonate any skill owner

  Scenario 2: Data exfiltration (line 325)
    Input: skill_name="'; UNION SELECT password FROM users; --"
    SQL becomes: "WHERE name = ''; UNION SELECT password FROM users; --'"
    Impact: User passwords leaked via UNION injection

  Scenario 3: Destructive injection (lines 600-615)
    Input: skill_id="1; DELETE FROM skills; --"
    SQL becomes: "WHERE id=1; DELETE FROM skills; --"
    Impact: Entire skills table deleted

  Scenario 4: Blind injection (lines 600-615)
    Input: skill_id="1 AND SLEEP(5); --" (SQLite: 1 AND 0; --)
    Impact: Response time reveals database structure

  Before (Line 325):

  After:
    local skill_exists=$(sqlite_select "$CFN_SKILLS_DB_PATH" "SELECT COUNT(*) FROM skills WHERE name = ?1;" "$skill_name")

  Before (Lines 600-615):
    new_tags=$(sqlite3 "$CFN_SKILLS_DB_PATH" "SELECT tags FROM skills WHERE id=$skill_id")

  After:
    new_tags=$(sqlite_select "$CFN_SKILLS_DB_PATH" "SELECT tags FROM skills WHERE id = ?1" "$skill_id")
    # Apply to lines 605, 610, 615 as well
