[MIGRATION NOTE: coordination-wait.sh Removal (v3.1.0)]
  Previous Issue (v3.0.x):
    - orchestrator.ts used Node.js execSync() to call coordination-wait.sh
    - Required explicit 'bash' prefix to avoid /bin/sh incompatibility
    - Shell-specific features (arrays, [[ ]]) caused execution failures

  Current Solution (v3.1.0+):
    - TypeScript-only implementation: src/cli/coordination-wait.ts
    - No shell script execution - pure Node.js/TypeScript
    - Type-safe coordination with compile-time checks
    - No bash vs sh compatibility issues

  Migration:
    - All coordination-wait.sh calls replaced with TypeScript module imports
    - Shell script archived to archive/legacy-bash/
    - Orchestrator uses native TypeScript coordination functions

  Validation:
    - Test: ./tests/docker-mode/implementations/coordination/wait-mechanism.sh
    - Expected: TypeScript coordination succeeds without shell scripts

    - 15 iterations: ~75 min
    - Buffer for Redis latency: +5-10 min

PART 7: COORDINATION PROTOCOL (REDIS PATTERNS)
================================================================================

[AGENT COMPLETION PROTOCOL]
  1. Agent completes work
  2. Agent executes: .claude/skills/cfn-redis-coordination/report-completion.sh \
                     --task-id <id> --confidence <0.0-1.0>
  3. Redis RPUSH: swarm:${TASK_ID}:loop3:complete "agent-type:confidence"
  4. Orchestrator BLPOP: swarm:${TASK_ID}:loop3:complete (blocking wait)
  5. Orchestrator receives completion signal
  6. Process continues to next phase

[GATE PASS SIGNALING]
  1. Orchestrator calculates test pass rate
  2. IF pass rate ≥ threshold:
     - Redis RPUSH: swarm:${TASK_ID}:gate-passed "PROCEED"
  3. Loop 2 validators BLPOP: swarm:${TASK_ID}:gate-passed (blocking wait)
  4. Loop 2 validators receive signal
  5. Loop 2 work begins

[BROADCAST CONTEXT INJECTION]
  1. Orchestrator builds broadcast message:
     {
       "iteration": N,
       "previous_results": [...],
       "gate_status": "PASSED|FAILED",
       "feedback": "..."
     }
  2. Redis SET: broadcast:${TASK_ID} <json>
  3. Agents read: Redis GET broadcast:${TASK_ID}
  4. Agents incorporate feedback into next iteration

[DELIVERABLE VALIDATION]
  1. Product Owner checks Redis keys:
     - results:${TASK_ID}:loop3 (implementation artifacts)
     - results:${TASK_ID}:loop2 (validation reports)
  2. IF keys missing or empty:
     - ABORT (prevents "consensus on vapor")
  3. IF keys present:
     - Review content
     - Make PROCEED/ITERATE/ABORT decision

PART 8: ANTI-PATTERNS AND TROUBLESHOOTING
================================================================================

[ANTI-PATTERN: "Consensus on Vapor"]
  Problem: Loop 2 validators approve work that doesn't exist
  Root Cause: No deliverable validation before Loop 2 spawning
  Solution: Gate check validates test execution + deliverables present
  Prevention: Orchestrator checks Redis keys before spawning Loop 2

[ANTI-PATTERN: Infinite Iteration Loop]
  Problem: Agents never reach consensus, loop forever
  Root Cause: No max iteration enforcement
  Solution: Orchestrator exits after MAX_ITERATIONS
  Prevention: Mode-specific iteration limits (5/10/15)

[ANTI-PATTERN: Coordinator Timeout]
  Problem: Coordinator agent exits before orchestration completes
  Root Cause: Long-running orchestration exceeds agent timeout
  Solution: Coordinator spawns orchestrator in background
  Prevention: Use orchestrate-wrapper.sh with explicit timeout param

[ANTI-PATTERN: Shell vs Bash Mismatch]
  Problem: coordination-wait.sh fails with "cannot execute binary file"
  Root Cause: Node.js execSync defaults to /bin/sh, not /bin/bash
  Solution: Prefix all shell script calls with explicit "bash" command
  Prevention: Always use "bash ${script}" in Node.js execSync

[TROUBLESHOOTING CHECKLIST]
  1. Redis running? (redis-cli PING)
  2. Task ID sanitized? (alphanumeric, hyphens, underscores only)
  3. Success criteria present? (prevents "consensus on vapor")
  4. coordination-wait.sh called with bash? (not just ${script})
  5. Agent profiles exist? (.claude/agents/cfn-dev-team/<type>.md)
  6. Redis keys populated? (context, broadcast, results)
  7. Max iterations reached? (check iteration counter)
  8. Timeout reasonable? (3600s default, 7200s for complex tasks)

[BUG #21: PRODUCTION TESTING REQUIREMENTS]
  Problem: Tests using mocks instead of production code paths
  Root Cause: Infrastructure tests used inline scripts, not real spawning
  Solution: Integration tests MUST use real agents and production paths
  Requirements:
    - Use actual spawning scripts (spawn-agent.sh)
    - Use production images (cfn-agent:latest, not alpine)
    - Validate actual CLI syntax (not inline scripts)
    - Check container logs for runtime errors
  Reference: tests/CLAUDE.md (test authoring standards)
  North Star: tests/cli-mode/core/e2e/test-cfn-loop-5-iteration-real-execution.sh
  Impact: Prevents mock-based validation that doesn't reflect production behavior
